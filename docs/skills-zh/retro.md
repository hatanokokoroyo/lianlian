# 复盘（Retro）

用户要求一次**复盘（retrospective）**。你要提出的是对编码 agent **环境（environment）**的改进，以改善今后的运行。

## 步骤

1. 调用 Skill 工具加载 `writing-for-agents` 取写作风格指南。

2. 读用户指定那一次会话的一手来源（primary source）。这可能意味着在本机翻找会话日志。用户没指定就默认当前会话。

3. 在下面这些类别里找改进候选。

- **导航（Navigation）**：agent 找到正确文件有多容易？文件之间有隐藏依赖吗？一个**导航指针（navigation pointer）**会不会让它更容易？*适用时机*：这次会话花了很长时间才找到某条信息。
- **自动化检查（Automated checks）**：有没有自动化检查本可以抓住 agent 犯的错？lint、类型检查、测试、文件系统 linter？先读仓库自己的检查命令（`package.json`／构建工具的 `lint`／`check` 脚本、CI workflow），所以「已经存在但没接线或悄悄坏掉」的检查才是那个发现，而不是重新发明一个。一个没有**护栏（guardrail）**（既无 pre-commit hook、也无跑 lint/类型检查/测试的 CI 作业）的仓库本身就是发现：没被 lint 的仓库是一项长期错失的机会，不是中性的默认状态（state）。*适用时机*：agent 犯了自动化检查本可抓住的错，或仓库根本没有护栏。
- **编码标准（Coding standards）**：该不该给**评审 agent** 一条要执行的新规则？该不该删掉或澄清既有规则？先给违规分类（category）：**机械性**的（固定的语法模式、被禁的 API、import 形状、文件位置规则）就该配确定性检查，没有别的选择 —— 仓库自有 linter 里的自定义规则、新的 pre-commit hook、或新的 CI 作业，看仓库的语言与既有护栏哪个最便宜。默认去建检查，而不是写规则。`CODING_STANDARDS.md` 留给真正的**判断性**问题（跨文件一致性、「与周边风格相符」、任何护栏永远替代不了的东西）。*适用时机*：评审 agent 漏掉了某个错。
- **全局 AGENTS.md**：有没有本该挪进编码标准（或自动化检查）的引导指令？*适用时机*：该文件特别大 —— 仓库里的或用户全局的。
- **工具经济（Tool economy）**：agent 有没有做过本可精简的昂贵工具调用？有没有特别吃 token 的自定义工具（CLI、MCP）？*适用时机*：agent 做过一次昂贵的工具调用。
- **空转（No-ops）**：找引导文件里那些不改变 agent 行为的指令。*适用时机*：引导文件又大又乱。
- **信息获取（Information access）**：寻找机会增加 agent 对信息的访问（tee 出 dev server 日志、对第三方服务的只读访问）。*适用时机*：有一条关键信息 agent 拿不到。

4. 按严重程度排序，把这些候选呈给用户。

## 参考

### 实现 vs 评审

记住所有工作都经过两个阶段：实现与评审。实现 agent 的**上下文压力**最大，它负责探索、写代码、调失败。

评审 agent 的上下文压力最小 —— 它拿到一份 diff，不需要探索，通常也不需要写代码或调试。

这意味着，施加编码标准的责任应当落在**评审 agent**，而不是实现 agent。

### 文件

你可以用仓库里的这几类文件：

- `CLAUDE.md`/`AGENTS.md`：这些文件会被推进任何在本仓库工作的 agent 的上下文窗口（context window）。应当极其节制地使用，通常只用于指向其他文件的**导航指针**。
- `CODING_STANDARDS.md`：这份文件在评审时读，而实现时不读。如果它超过 1,000 行，就往 docs 目录里加**导航指针**。
- Docs：把 docs 当参考文件用，由其他文件指向它们。先找已存在的 docs，再考虑写新的。
- Skills：用 skill 承载文档（因为它的 description 会进入 agent 的上下文窗口），或承载用户主动调用的命令。遵循 `writing-for-agents` 技能里的建议。
