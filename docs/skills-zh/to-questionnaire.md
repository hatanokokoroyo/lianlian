# 变成问卷（to-questionnaire）

把用户无法独自回答的事情变成一份**问卷（questionnaire）**：一份 markdown 文档，他交给某个人异步填写，或在一次会议里一起填完。接收方握有用户缺少的知识；问卷把它抽出来。

**拷打（grilling）「发送」，不要拷打「主题」。** 只就*发送这件事*访谈用户 —— 那部分他永远答得出：这份东西发给谁、需要拿回什么。文档里的问题再去瞄准接收方所知与用户所需之间的**缺口**。

1. **它发给谁？** 用一次交流问出接收方的角色（role）、专长，以及与用户的关系。这决定问卷的语气，也决定它必须携带多少上下文。判据：你知道接收方是谁，以及他知道哪些用户不知道的东西。

2. **你需要拿回什么？** 用一次交流问出用户独自定不了、必须从这个人那里得到的具体决策或事实。判据：你有一份具体清单，写明用户读完答案后必须能够做到或决定什么。

3. **写问卷。** 按第 1、2 步定出的缺口起草问题，遵循下面的文档结构。写到当前目录的 `to-questionnaire-<slug>.md`（slug 取自主题），并报告该路径。判据：文件存在，且第 2 步里用户点名的每一项都有问题覆盖。

## 文档结构

把整份文档定位成一份**发现问卷（discovery questionnaire）**：用户缺上下文，接收方有。问题按重要性从高到低排 —— 异步意味着你可能只有一次机会；问题多起来后，用 `##` 标题按主题分组。使用下面的模板。

<questionnaire-template>

# <问卷标题>

**目的：**这份问卷为什么存在，以及压在它上面的那个决策。

**来自：**<用户>，**发往：**<接收方>，**你的回答会被如何使用：**<去向>

## 背景

一段话，给一个不在用户脑子里的人做定位。够他答得好，但不要写成一页。

## 如何作答

截止时间与大致工作量。部分回答和「我不知道」都有用：拿不准的就标出来，而不是跳过。

## <主题标题>

每个主题一个 `##` 小节。每节下面是该主题的问题，重要性从高到低。每个问题只含一个想法，绝不要复合问题；问题正下方留作答占位；只在问题可能被误读、或容易被敷衍时，补一行*为什么这件事重要*。

<question-example>
### 上线时系统预计要承受多大的负载？

_为什么重要：这决定我们现在就为突发流量做容量，还是推迟。_

>
</question-example>

## 还有什么？

收尾的兜底问题：有没有我们没问到、但我们应该知道的？

</questionnaire-template>
