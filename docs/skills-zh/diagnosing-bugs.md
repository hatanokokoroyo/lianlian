# 诊断 bug（Diagnosing Bugs）

治难 bug 的纪律。只有拿出明确理由时才能跳过某个阶段。

探索代码库时读 `GLOSSARY.md`（若存在），建立相关模块（module）的清晰心智模型，并检查你所触及区域的 ADR。

## 脱敏（Redact）

本技能会让你展示命令、输出与捕获的产物。**先给每个 secret 打码**：在原处写 `<REDACTED>`。把循环建立在环境变量上，让凭证留在环境里，而不是出现在你展示的东西里。捕获的产物带着 auth 头：只引用携带信号的那几行。

若脱敏后的输出不足以诊断这个 bug，就明说，然后问用户。

## 阶段 1：建立反馈循环（feedback loop）

**这一阶段才是本技能。** 其余都是机械劳动。只要你有一个**紧（tight）**的通过/失败信号（一个能在*这个* bug 上变红的信号），你就能找到原因；二分、假设检验、插桩都只是消费它。没有它，盯着代码看多久都救不了你。

在这里投入不成比例的精力。**要狠。要巧。不许放弃。**

### 构造它的方式，大致按这个顺序

1. **失败测试（failing test）**：放在任何能触达该 bug 的接缝（seam）上 —— 单元、集成、e2e。
2. **Curl / HTTP 脚本**：打一个正在跑的 dev server。
3. **CLI 调用**：喂一份 fixture 输入，把 stdout 与已知正常的快照 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）：驱动 UI，对 DOM / console / network 做断言。
5. **重放捕获的 trace**：把一次真实网络请求 / payload / 事件日志存到磁盘，隔离地重放进该代码路径。
6. **一次性 harness**：拉起系统的一个最小子集（一个服务、mock 掉依赖），用单次函数调用跑通该 bug 的代码路径。
7. **属性 / fuzz 循环**：如果 bug 是「偶尔输出错」，跑 1000 个随机输入找失败模式。
8. **二分 harness**：如果 bug 出现在两个已知状态（提交、数据集、版本）之间，把「在状态（state） X 启动、检查、重复」自动化，好让 `git bisect run` 驱动它。
9. **差分循环**：同一输入分别走旧版本与新版本（或两套配置），diff 输出。
10. **HITL bash 脚本**：最后手段。若必须人点，就用 `scripts/hitl-loop.template.sh` 驱动*那个人*，让循环仍然结构化。捕获的输出回喂给你。

把反馈循环建对，bug 就修好了 90%。

### 收紧（tighten）循环

把循环当产品对待。一旦你*有了*一个循环，就**收紧**它：

- 能更快吗？（缓存初始化、跳过无关启动、缩小测试范围。）
- 信号能更锋利吗？（断言那个具体症状，而不是「没崩」。）
- 能更确定吗？（钉住时间、给 RNG 播种、隔离文件系统、冻结网络。）

一个 30 秒还不稳的循环，比没有循环好不了多少；一个 2 秒的确定性循环是紧的，是调试超能力。

### 非确定性 bug

目标不是干净的复现，而是**更高的复现率**。把触发跑 100 次、并行化、加压力、收窄时序窗口、注入 sleep。50% 概率复现的 bug 可调试；1% 的不可，所以持续提高复现率直到可调试。

### 当你确实建不出循环时

停下来，明确说出来。列出你试过什么。向用户要：(a) 能复现它的那个环境的访问权，(b) 一份脱敏的捕获产物（HAR 文件、日志转储、core dump、带时间戳的录屏），或 (c) 允许你临时加生产环境插桩。**不要**在没有循环的情况下进入假设阶段。

### 完成判据：一条会变红的紧循环

阶段 1 完成的标准是：循环**紧**且**能红** —— 你能说出**一条命令**（脚本路径、测试调用、curl），你**已经至少跑过一次**（展示该调用及其输出，脱敏后），并且它满足：

- [ ] **能红**：它驱动真正的 bug 代码路径，并断言**用户描述的那个确切症状**，因此能在这个 bug 上变红、修好后变绿。不是「跑起来不报错」；它必须能*抓住这个具体 bug*。
- [ ] **确定性**：每次跑判定相同（对 flaky bug：按上文，复现率高且固定）。
- [ ] **快**：秒级，不是分钟级。
- [ ] **agent 可跑**：你能无人值守地运行它；只有 `scripts/hitl-loop.template.sh` 时才需要人在环。

如果你发现自己在这条命令存在之前就开始读代码构建理论，**停下：直接跳到假设正是本技能要防的那种失败。** 没有能红的命令，就没有阶段 2。

## 阶段 2：复现 + 最小化（minimise）

跑这个循环。看着它随 bug 出现而变红。

确认：

- [ ] 循环产生的失败模式是**用户**描述的那个，而不是恰好相邻的另一个失败。搞错 bug = 修错东西。
- [ ] 这个失败在多次运行中可复现（对非确定性 bug：复现率足够高到能据此调试）。
- [ ] 你已经捕获确切症状（错误消息、错误输出、慢的耗时），以便后续阶段验证修复真的解决了它。

### 最小化

一旦它变红，就把复现缩到**仍然会变红的最小场景**。输入、调用者、配置、数据、步骤**一次砍一样**，每砍一次重跑循环，只保留对失败承重的东西。

为什么值得：最小复现缩小阶段 3 的假设空间（剩下可疑的活动部件更少），并直接成为阶段 5 的干净回归测试（regression test）。

完成标准是**剩下的每个要素都承重**：去掉任何一个，循环就变绿。

在你既**复现**又**最小化**之前，不要往下走。

## 阶段 3：假设（hypothesise）

在检验任何一个之前，先生成 **3~5 个排好序的假设**。只生成一个假设会锚定在第一个看起来合理的想法上。

每个假设必须**可证伪**：说出它做的预测。

> 格式：「若 <X> 是原因，那么 <改动 Y> 会让 bug 消失 / <改动 Z> 会让它更糟。」

如果你的假设说不出预测，那它只是一阵感觉：丢掉或磨锋利。

**在检验之前把排序后的清单给用户看。** 他们常有领域知识能立刻重排（「我们刚部署了 #3 的改动」），或者知道已经排除过的假设。这是个便宜的检查点，省很多时间。不要卡在这里；用户不在就按你的排序继续。

## 阶段 4：插桩（instrument）

每个探针（probe）都必须对应阶段 3 的某个具体预测。**一次只改一个变量。**

工具偏好：

1. **调试器 / REPL 查看**，若环境支持。一个断点胜过十行日志。
2. **有针对性的日志**，打在那几个能区分假设的边界上。
3. 绝不「全打日志再 grep」。

**给每条调试日志打唯一前缀标签**，例如 `[DEBUG-a4f2]`。收尾时的清理就变成一次 grep。没打标签的日志会活下来；打了标签的会死掉。

**性能分支。** 对性能回归，日志通常是错的工具。改为：先建立基线测量（计时 harness、`performance.now()`、profiler、查询计划），然后二分。先测量，后修。

## 阶段 5：修复 + 回归测试

在修复**之前**写回归测试 —— 但前提是存在**正确的接缝**。

正确接缝，指的是测试能按 bug 在调用点发生的方式，演练**真实的 bug 模式**。若唯一可用的接缝太浅（bug 需要多个调用者却只能单调用者测试；单元测试无法复现触发 bug 的那条链），在那里的回归测试只会给出虚假的信心。

**若不存在正确接缝，这件事本身就是结论。** 记下来。是代码库架构在阻止这个 bug 被锁死。把它留给下一个阶段。

若存在正确接缝：

1. 把最小复现变成该接缝上的失败测试。
2. 看它失败。如果你是通过改代码或 fixture 强行造红的，先与一份原始副本 `diff`，证明改动真的落地了，再信任它。
3. 应用修复。
4. 看它通过。
5. 针对原始（未最小化的）场景重跑阶段 1 的反馈循环。

## 阶段 6：清理（cleanup）

宣布完成前必须做到：

- [ ] 原始复现不再复现（重跑阶段 1 的循环）
- [ ] 回归测试通过（或已记录接缝缺失）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（grep 该前缀）
- [ ] 一次性原型已删除（或移到明确标记的 debug 位置）
- [ ] 最后被证明正确的那个假设，写进 commit / PR 消息，让下一个调试者学到东西
