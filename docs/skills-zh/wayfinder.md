# 路径勘察（Wayfinder）

一个松散的想法到来了，大到装不进一个 agent 会话，而且裹在迷雾里：从这里到**目的地（destination）**的路还看不见。勘察（wayfinding）是去找那条路，不是朝目的地猛冲。本技能把这条路画成仓库 issue tracker 上的**共享地图（map）**，然后一次一个地解决它的**决策工单（decision ticket）**（那些答案是「一个决策」而不是「一段要执行的构建」的问题），直到路线清楚。

目的地因事而异，而给它命名是画图的第一件事：它塑造每一张工单（ticket）。它可能是一份交出去再迭代的 spec，一个在规划开始前要钉死的决策，或一处就地完成的改动（例如数据结构迁移）。地图与领域无关：工程工作、课程内容，任何符合这个形状的东西。

## 规划，而不是动手（Plan, don't do）

Wayfinder 默认是**规划**：每个工单解决一个决策，路清楚了地图就完成 —— 在有人去实际动手之前，没有剩下要定的事。那种「干脆直接把活干了」的拉力，通常正是你已经走到地图边缘、该交棒的信号。一次工作可以在它的 **Notes** 里覆盖这个默认，把执行也纳入地图，但除此之外，产出决策，而不是交付物。

## 用名字指代（Refer by name）

每张地图与每个工单都是一条 issue，所以它有一个**名字**：它的标题。在人读到的一切内容里（叙述、地图的 Decisions-so-far），用那个名字指代它，绝不用裸 id、编号或 slug。一整面 `#42, #43, #44` 是不可读的；名字一眼就懂。id 与 URL 不会消失；名字裹住它的链接，但它们**藏在名字里**，绝不代替名字。

## 地图（The Map）

地图是本仓库 issue tracker 上的单条 issue，标签 `wayfinder:map`，是权威产物。它的工单是地图的**子 issue（sub-issue）**。

地图是**索引**，不是仓库。它列出已做出的决策，并指向持有其细节的工单；一个决策只活在一个地方（它的工单），所以地图从不复述它，只给要点加链接。

**地图、其子工单、阻塞（blocked）关系与前沿（frontier）查询在物理上住在哪里，因 tracker 而异。** issue tracker 本应已经提供给你；若没有，见 `docs/agents/issue-tracker.md` 的「Wayfinding 操作」一节，看**本仓库**怎么表达它们（`/setup-matt-pocock-skills` 已卸载，不要引导用户运行它）。若没有任何 tracker，默认用本地 markdown tracker。

### 地图正文

整张地图的低分辨率视图，每个会话加载一次。未关闭的工单**不**列在这里：它们是未关闭的子 issue，由查询找到。

<领域；每个会话都该查阅的技能；这次工作的常设偏好>

### 工单

每个工单是地图的**子 issue**；tracker 的 issue id 就是它的身份。正文是那个问题，规模控制在一个 100K token 的 agent 会话内：

```markdown
## 问题

<本工单要解决的那个决策或调查>
```

每个工单带一个 `wayfinder:<type>` 标签，取值 `research`、`prototype`、`grilling`、`task` 之一（见[工单类型](#工单类型)）。`wayfinder:` 标签是地图与工单**唯一**携带的标签，绝不打 `ready-for-agent` 这类 triage 标签：它们是决策，不是实现工作。

一个会话**认领（claim）**工单的方式是把它指派给驱动这张地图的开发者，**在任何工作之前**，这样并发会话会跳过它。那个指派人*就是*认领：未关闭且未指派的工单就是未认领。

阻塞使用 tracker 的**原生**依赖关系：这一点至关重要，因为它让前沿在 tracker 自己的 UI 里**可视化**呈现，人不必打开地图就知道哪些可以拿。只有缺少原生阻塞的 tracker 才退回在正文里写约定。一个工单的所有阻塞者（blocker）都已关闭时，它才**解除阻塞**（unblocked）；**前沿**就是未关闭、未阻塞、未认领的子工单 —— 已知世界的边缘。

答案不在正文里；它在解决时被记录（见[推进地图](#推进地图)）。解决工单时产生的资产用链接挂在 issue 上，不要粘贴进正文。

## 工单类型

每个工单要么是 **HITL**（human in the loop，和一个能为自己说话的真人*一起*做），要么是 **AFK**，由 agent 独立驱动。HITL 工单只能通过那场实时交流来解决；agent 绝不代替人那一侧（一个自问自答的 grilling agent 已经破了这条）。

- **Research**（AFK）：读文档、第三方 API，或本地资源（如知识库），以浮出一个决策所等待的事实。由调用 Skill 工具加载 "research" 的 subagent 解决。需要当前工作目录之外的知识时用它。
- **Prototype**（HITL）：通过做一个便宜、粗糙、具体的东西来让人反应（一份提纲、一个粗略版本、一个 stub，或 UI/逻辑代码），从而提高讨论的保真度 —— 调用 Skill 工具加载 "prototype"。把原型作为资产链接上。当「它该长什么样」或「它该怎么表现」是核心问题时用它。
- **Grilling**（HITL）：对话。默认情况。总是调用 Skill 工具两次，分别加载 "grilling" 与 "domain-modeling"。
- **Task**（HITL 或 AFK）：在一个**决策**能做出之前必须完成的手工活：没有东西要决定、要原型、要研究，但讨论被卡住直到它做完。注册某个服务以便评判它的 API、开通访问权、搬数据以便看清形状。这是唯一「动手而非决策」的类型，它靠解锁一个决策来挣得位置，而不是靠交付目的地。agent 能独立做的就独立做（AFK）；否则给人一份精确的清单（HITL）。工作完成时解决；答案记录做了什么，以及后续工单会依赖的事实（凭证位置、新 URL、行数）。

## 战争迷雾（Fog of war）

地图是*刻意*不完整的：还看不见的东西就别画。在活跃工单之外是**战争迷雾（fog of war）**：那些你能察觉即将到来、但还钉不住的决策与调查的黯淡视野，因为它们挂在尚未解决的问题上。解决一个工单会清掉它前方的雾，把现在可指定的东西一次一片地毕业成新工单，直到通往目的地的路清楚、不再剩工单。

地图的**尚未明确（Not yet specified）**一节就是写下这片黯淡视野的地方：怀疑中的问题、以后要回看的区域。它是**通往**目的地的未发现前沿：这里的一切都在范围内，只是还不够锋利、开不出工单。视野允许多松就写多松、多全就写多全；它同时是给协作者的路标，让人看出这次工作往哪去。

**是雾还是工单？** 判据是你**现在**能不能把问题说清楚，*不是*你**现在**能不能回答它。

- **开成工单**：问题已经锋利，即使它被阻塞、你还动不了。
- **放进尚未明确**：你还说不出那么锋利。不要预先把雾切成工单大小的块：它比工单更粗糙，一片雾在前沿抵达时可能毕业成好几个工单，也可能一个都不成。

**尚未明确**排除已经定下的（已定决策）、已经是活跃工单的、以及范围之外的（下一节）。

## 范围之外（Out of scope）

雾只会朝目的地聚集。目的地确定范围，所以超出它的工作属于**范围之外**：它不是雾，也不属于**尚未明确**。它在地图上有自己的**范围之外**一节：你**自觉地**排除在这次工作之外的东西。让它落在那里的，是范围，不是锋利度。

范围之外的工作永不毕业（前沿止于目的地），所以只有当目的被重新划定、且以一次全新工作而非续做的形式，它才会回来。

把某件事判为范围之外，是一次划定范围的动作，而不是路线图上的一步。当一张已存在的工单被发现坐落在目的地之外时（画图时错划进来，或被某次解决暴露出来），**关闭它**（已关闭工单明确不在前沿上），并在**范围之外**一节留一行：要点 + 为什么出了范围 + 链接到那张已关闭工单。它不进**已定决策**，那一节记录的是真正走过的路线；范围边界不是路线图上的一步。

## 调用方式

两种模式。无论哪种，**每个会话绝不要解决超过一个工单**，research 工单除外。

### 画地图（Chart the map）

用户带着一个松散想法调用。

1. **给目的地命名。** 调用 Skill 工具两次，加载 "grilling" 与 "domain-modeling"，钉死这张地图要找的是什么：那份 spec、那个决策、或那处改动。目的地确定范围，所以它最先落定。
2. **测绘前沿。** 再拷打（grilling）一次，这次**广度优先**：在整个空间铺开而不是在单一线索上深入，浮出未定的决策与现在就能走的第一步。**如果这没浮出任何雾**（通往目的地的路已经清楚，整段旅程小到一个会话装得下），你不需要地图。停下，问用户想怎么推进。
3. **创建地图**（标签 `wayfinder:map`）：填好目的地与备注，已定决策留空，把雾草画进**尚未明确**。
4. **创建你现在能指定的工单**，作为地图的子 issue，然后在**第二遍**里连阻塞边（issue 得先有 id 才能互相引用）。交叉引用也在这一遍写，用真实 id：占位的 `#<n>` 会自动链到一条无关 issue。连线把它们分进前沿与被阻塞；还指定不了的留在雾里 —— **尚未明确**一节。
5. **发射研究 subagent。** 对你刚创建的每个 `research` 工单，起一个带全新上下文窗口（context window）的 subagent，调用 Skill 工具加载 "research" 并行解决它，把发现捕获在一个用完即弃的 `research/<name>` 分支上，并从工单里放一个上下文指针。推这个分支但不开 PR：它永不被合并。
6. 停。画图是一个会话的活；它不解决任何东西。

### 推进地图（Work through the map）

用户带着一张地图（URL 或编号）调用。工单是**可选的**：没给的话，由你挑下一个决策，而不是用户。

1. 加载**地图**：低分辨率视图，不是每个工单的正文。
2. 选工单。用户点名了就用他点的；否则按顺序取前沿上的第一个。**认领它**：在任何工作之前指派给自己。
3. 按它 `wayfinder:<type>` 标签所名的类型来解决（见[工单类型](#工单类型)）。读标签，不要只看正文：正文从不声明类型。**按需缩放**：随时取回任何相关或已关闭工单的完整正文；调用 Skill 工具加载 `## 备注` 块点名的技能。拿不准就调用两次，加载 "grilling" 与 "domain-modeling"。
4. 记录解决：把答案作为**解决评论（resolution comment）**发出，**关闭**该 issue，并往地图的已定决策里**追加一个上下文指针**。
5. 添加新浮出的工单（先创建再连线）；把答案使其可指定的雾毕业掉，并从**尚未明确**里清掉每一片已毕业的雾，让它只作为新工单存在。若答案揭示某张工单（这张或别的）坐落在目的地之外，**把它判为范围之外**，而不是在路线上解决它。若该决策让地图的其他部分失效，更新或删除那些工单。

用户可能会并行跑未阻塞的工单，所以要预期其他会话在并发编辑 tracker。
