# code-review

对 `HEAD` 与用户给出的固定点之间的 diff 做双轴评审：

- **Standards（标准）**：代码是否符合本仓库成文的编码标准？
- **Spec（规格（spec））**：代码是否忠实实现了来源 issue / spec？

两轴各跑在一个**并行 subagent** 里，彼此不污染上下文，然后由本技能汇总它们的发现。每个 subagent 都从全新的上下文窗口（context window）开始。

issue tracker 本应已经提供给你。若没有，去读 `AGENTS.md` 与 `docs/agents/issue-tracker.md`（`/setup-matt-pocock-skills` 已卸载，不要引导用户运行它）。

## 过程

### 1. 钉住固定点

用户说的固定点是什么就是什么（提交 SHA、分支名、tag、`main`、`HEAD~5` 等）。若未指定，问。

一次性确定 diff 命令：`git diff <固定点>...HEAD`（三点，这样比较的是 merge-base）。同时用 `git log <固定点>..HEAD --oneline` 记下提交列表。

继续之前，先确认固定点能解析（`git rev-parse <固定点>`）且 diff 非空。坏引用或空 diff 应当在这里失败，而不是在两个并行 subagent 内部失败。

### 2. 确定 spec 来源

按以下顺序找来源 spec：

1. 提交消息里的 issue 引用（`#123`、`Closes #45`、GitLab 的 `!67` 等），按 tracker 文档的工作流取回。
2. 用户以参数形式传的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能相匹配的 spec 文件。
4. 什么都没找到就问用户 spec 在哪。若他说没有，**Spec** subagent 将跳过并报告「无 spec 可用」。

### 3. 确定标准来源

搜索仓库里每一份记录「代码应当怎么写」的文件。存在 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md` 时，它们必须在清单上。

在仓库成文内容之上，Standards 轴始终携带下面的**坏味道（code smell）基线**：一组固定的 Fowler 代码坏味道（《重构》第 3 章），即使仓库什么都没写也适用。两条规则约束它：

- **仓库优先。** 成文的仓库标准永远胜出；当它认可某件基线会指出的做法时，抑制该坏味道。
- **永远是判断性意见。** 每个坏味道都是带标签的启发式判断（「可能是 Feature Envy」），绝非硬性违规。与这里任何标准一样，工具已经强制的东西就跳过。

每个坏味道按*它是什么* → *怎么修*来读；拿它比对 diff：

- **神秘命名（Mysterious Name）**：函数、变量或类型的名字没揭示它做什么或存什么。→ 改名；若起不出诚实的名字，是设计本身浑浊。
- **重复代码（Duplicated Code）**：同一逻辑形状出现在本次改动的多个 hunk 或文件里。→ 抽出共享形状，两边都调用它。
- **依恋情结（Feature Envy）**：某方法访问另一个对象的数据比访问自己的还多。→ 把该方法挪到它羡慕的数据上。
- **数据泥团（Data Clumps）**：同样那几个字段或参数总是一起旅行（一个想诞生的类型）。→ 把它们打包成一个类型，传那个类型。
- **基本类型偏执（Primitive Obsession）**：用基本类型或字符串顶替一个值得有自己类型的领域概念。→ 给这个概念一个自己的小类型。
- **重复的 switch（Repeated Switches）**：针对同一类型的同一 `switch`／`if` 级联在改动中反复出现。→ 换成多态，或两处共享的一张映射表。
- **霰弹式修改（Shotgun Surgery）**：一次逻辑改动迫使你在 diff 里散落地改很多文件。→ 把一起变化的东西聚到一个模块（module）里。
- **发散式变化（Divergent Change）**：同一个文件或模块因几个不相关的原因被改。→ 拆开，让每个模块只因一个原因变化。
- **夸夸其谈通用性（Speculative Generality）**：为 spec 里没有的需求加了抽象、参数或钩子。→ 删掉，内联回去，直到真需求出现。
- **过长的消息链（Message Chains）**：调用者不该依赖的 `a.b().c().d()` 长导航。→ 把这段游走藏在第一个对象的一个方法后面。
- **中间人（Middle Man）**：一个类或函数大部分只是往下转发。→ 去掉它，直接调真正的目标。
- **被拒绝的遗赠（Refused Bequest）**：子类或实现者忽略或覆盖了它继承的大部分东西。→ 放弃继承，改用组合。

### 4. 并行启动两个 subagent

把两个 subagent 调用一起发出，放在前台，然后汇总它们返回的报告。

**Standards subagent 的提示词**应包含：

- 完整的 diff 命令与提交列表。
- 第 3 步找到的标准来源文件清单，**加上第 3 步的坏味道基线全文**（subagent 没有别的途径拿到它）。
- 任务简报（brief）：「按文件/hunk 逐处报告：(a) diff 违反成文标准的每一处：引用该标准（文件 + 规则）；(b) 你发现的任何基线坏味道：点名并引用该 hunk。区分硬性违规与判断性意见：成文标准的违背可以是硬性的，但基线坏味道永远是判断性意见，且成文的仓库标准优先于基线。工具已强制的跳过。400 字以内。」

**Spec subagent 的提示词**应包含：

- diff 命令与提交列表。
- spec 的路径或取回的全文。
- 任务简报：「报告：(a) spec 要求但缺失或只做了一半的需求；(b) diff 里没被要求的行为（范围蔓延）；(c) 看起来实现了但实现有误的需求。每项发现都引用对应的 spec 原文。400 字以内。」

若 spec 缺失，跳过 Spec subagent 并在最终报告中注明。

### 5. 汇总

在两个标题 `## Standards` 与 `## Spec` 下呈现两份报告，照原样或轻度清理。**不要**合并或重新排序这些发现，因为两轴是刻意分开的（见《为什么分两轴》）。

结尾给一行总结：每轴的发现总数，以及**每轴内部**最严重的问题（若有）。不要跨轴挑出唯一赢家 —— 那正是这种分离要防止的重新排序。

## 为什么分两轴

一次改动可以通过一轴而失败于另一轴：

- 遵守每条标准、却实现错了东西的代码 → **Standards 通过，Spec 失败。**
- 完全照 issue 要求做、却破坏了项目惯例的代码 → **Spec 通过，Standards 失败。**

分开汇报，才能防止一轴掩盖另一轴。
