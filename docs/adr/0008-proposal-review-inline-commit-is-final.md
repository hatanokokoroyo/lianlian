# 提议卡的审核在对话时间线里，提交即定案

档案更新提议以一张卡片的形式出现在会话时间线里，位置就在本轮回答之后；审核期间底部输入框禁用。用户一次处理完整张卡：勾选=采纳，不勾=拒绝，一个按钮提交。提交本身是一个事务——采纳项落判定与依据，拒绝项落拒绝证据，卡从「待审」变成「已处理」。随后系统把整张卡的结果作为一条用户消息交给模型，跑一轮回复。没有撤销。

**背景**：旧实现把卡片钉在消息列表与输入条之间。它在滚动区之外，长卡既遮挡视线又滚不动，8 项时底部按钮会被挤掉。拒绝一项就自动发起一轮，一次审核在模型那里变成了好几次对话；接受一项反而静默。撤销则是常驻在卡上的第二块界面，改完也不想看见它。

**代价**（接受）：提交后不能反悔，纠错只能再说一句让模型追加「更正」；审核期间不能边问边审，想问就得先把卡处理掉；卡片行成为会话记录的一部分，旧对话里没有这一行。

**被拒的替代方案**：

- **保留撤销，但「发起下一条对话后失效」**——这条规则在界面上不可见，用户只会在失效那一刻发现。而且撤销要么静默改档案（模型下一轮看到的世界与它以为的不一致，正是要避免的矛盾），要么再写一条「我撤销了」的消息（一次决策变成三次交互）。
- **审核界面做成浮层，或做成「去审」的跳转入口**——用户需要对照上方那段判断依据来回跳；跳转比滚动更贵，而且浮层会一直挡住视线。
- **卡片存成普通消息并新增一种角色**——要升 schema、整库重建，还把界面状态混进了「谁说的话」。
