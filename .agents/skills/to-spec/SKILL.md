本技能拿当前对话上下文与对代码库的理解，产出一份 spec。**不要**访谈用户，只综合你已经知道的东西。

issue tracker 与 triage 标签词表本应已经提供给你。若没有，说明配置缺失 —— 本仓库的配置在 `AGENTS.md` 与 `docs/agents/` 中（`issue-tracker.md`、`triage-labels.md`、`domain.md`），去读它们，而不是引导用户运行 `/setup-matt-pocock-skills`（该技能已卸载）。

## 过程

1. 如果还没做过，先探索仓库以了解代码库现状。spec 全篇使用项目的领域词表，并遵守你所触及区域的 ADR。

2. 勾出你要用来测这个功能的**接缝（seam）**。已有接缝优先于新接缝；用能用的最高接缝。若需要新接缝，在你能提出的最高处提出。整个代码库的接缝越少越好 —— 理想数量是一个。

与用户确认这些接缝符合他的预期。

3. 用下面的模板写 spec，然后发布到项目的 issue tracker。打上 `ready-for-agent` triage 标签 —— 不需要额外 triage。

<spec-template>

## 问题陈述

用户所面对的问题，从用户的视角描述。

## 解决方案

对该问题的解决方案，从用户的视角描述。

## 用户故事

一份长长的、编号的用户故事清单。每个用户故事采用这种格式：

1. 作为 <角色>，我想要 <功能>，以便 <收益>

<user-story-example>
1. 作为手机银行客户，我希望在账户上看到余额，以便对自己的消费做出更明智的决定
</user-story-example>

这份用户故事清单应当非常详尽，覆盖该功能的方方面面。

## 实现决策

已做出的实现决策清单，可包括：

- 将要构建/修改的模块
- 这些模块中将被修改的接口
- 来自开发者的技术澄清
- 架构决策
- Schema 变更
- API 契约
- 具体交互

**不要**写具体文件路径或代码片段，它们会很快过期。

例外：若原型产出的片段比散文更精确地编码了某个决策（状态机、reducer、schema、类型形状），就把该片段内联进相关决策，并简短注明它来自原型。只保留决策密集的部分，不要可运行的 demo，只要关键片段。

## 测试决策

已做出的测试决策清单，包括：

- 什么算好测试（只测外部行为，不测实现细节）
- 哪些模块会被测试
- 测试的先例（即代码库中同类测试）

## 不在范围内

本 spec 明确排除在外的内容。

## 补充说明

关于该功能的任何其他说明。

</spec-template>
