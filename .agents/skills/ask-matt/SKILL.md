# Ask Matt

你记不住每一个 skill，所以来问。

在陈述某个 skill 做什么、或建议跳过某一步之前，先读那个 skill 的 SKILL.md：这里的摘要只用于定位。

**流程（flow）** 是穿过若干 skill 的一条路径。大多数路径沿着一条**主流程**走，另有两条**入口（on-ramp）**并入主流程。其余的都是独立技能，或跑在底层的词汇层。

## 主流程：从一个想法到上线

大多数工作走这条路。你有一个想法，想把它做出来。

1. **`/grill-with-docs`** 通过访谈把想法磨锋利。只要你在**某个工作目录里**工作，就从这里开始：它是有状态的，会把学到的东西留在 `GLOSSARY.md` 和 ADR 里。（没有工作目录？改用 `/grill-me`，见「独立技能」一节。两者跑的是同一个 `/grilling` 原语；`grill-with-docs` 是留下纸面痕迹的那个，只要有个仓库可留，它就是两者中更好的。）
2. **分支：所有问题都能在对话里敲定吗？** 如果某个问题需要一个可运行的答案（状态、业务逻辑、必须亲眼看过的 UI），就绕道去跑原型，两个方向都用 **`/handoff`** 搭桥（原型活在自己的目录里，而这正是 `/handoff` 的用途，见「阶段边界」）：
   - 用 **`/handoff`** 交出去，然后对着那份文件开一个新会话，
   - 用 **`/prototype`** 以一次性代码回答那个问题，
   - 再用 **`/handoff`** 把学到的东西交回来，并从最初的想法线程里引用它。
3. **分支：这是一次跨多个会话的构建吗？**
   - **是** → 用 **`/to-spec`**（把线程变成 spec），再用 **`/to-tickets`** 拆成 tracer-bullet 工单，每个工单声明自己的**阻塞边**。然后用两种方式之一推进：
     - **`/implement`** 一次一个工单，**每个工单之间 `/clear` 清上下文**。本地 tracker 下，那是 `.scratch/<feature>/issues/` 里一个工单一个文件，按阻塞顺序手工推进；真实 tracker 下，阻塞边变成原生阻塞链接，于是任何阻塞项都已完成的工单都可以直接抓。每个工单都是自包含的，所以上一个工单的上下文是可丢弃的。
     - **`/implement-spec`** 一次跑完整个 spec。它把工单读成**任务图**，在就绪的**前沿（frontier）**上并行跑实现 subagent，最后全部落到一个**集成分支**上。当你更想编排构建、而不是亲手驱动每个工单时用它。
   - **否** → 就在当前上下文里直接 **`/implement`**。

   两种方式下，代码都是由驱动 **`/tdd`**（一次一个红灯-绿灯切片）建出来的，并以 **`/code-review`** 收尾 —— 对 diff 做双轴（Standards + Spec）评审。`/implement` 对每个工单都跑这两步；`/implement-spec` 的各个实现者各自驱动 `/tdd`，然后对集成分支跑一次 `/code-review`。只想测试先行地建一个具体行为、不需要完整 spec 时，单独用 **`/tdd`**；想针对某个固定点评审分支或 PR 时，单独用 **`/code-review`**。

   工作以 PR 形式上送时，**`/pr`** 负责塑造 PR 正文：能体现改动的最小可视化，改动前后可用的证据，以及单向门/双向门的判断。它是模型自动调用的，所以 agent 写 PR 时自己会去取。

4. **`/retro`** 收尾闭环。构建之后 —— 尤其是走歪了的构建 —— 它回看整个会话，提出的改动针对 agent 的**环境**而非代码：导航指针、自动化检查、`/code-review` 执行的编码标准、引导文件、工具链。机械性的错误变成确定性检查；判断性的问题变成编码标准。下一次构建因此从一个更好的环境开始。

### 上下文卫生

第 1~3 步保持在**同一个不间断的上下文窗口**里（在 `/to-tickets` 之前不要 compact 或 clear），这样访谈、spec 和工单都建立在同一套思考上。之后每个 `/implement` 都从工单出发、全新开始。`/retro` 在它回看的那个会话里跑，在 clear 之前跑；clear 之后就用那次会话的日志喂它。

这条的边界是 **[smart zone](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型仍然敏锐推理的窗口（当前最强模型约 150k tokens）。如果会话在 `/to-tickets` 之前就逼近它，不要在降智状态下硬推；在最接近的阶段边界处 `/compact` 再继续（见「阶段边界」）。

## 入口（on-ramps）

一个会产生工作、然后并入主流程的起始处境。

- **bug 和需求堆积起来了** → **`/triage`**。它把 issue 沿 triage 角色推进，产出 ready-for-agent 的 issue，之后由 **`/implement`** 接走。

  triage 只用于**不是你创建的** issue：bug 报告、外部功能请求、任何原样到来的东西。`/to-tickets` 产出的工单已经是 ready-for-agent，所以**不要**再 triage 它们。

- **东西坏了** → **`/diagnosing-bugs`**。用于难的那些：第一眼看不出来的 bug、时好时坏的 flake、在两个已知正常状态之间偷偷引入的回归。在拿到**紧反馈循环**（一条已经能在*这个* bug 上变红的命令）之前，它拒绝开始推测，然后靠回归测试修好。修完就在同一会话里跑 **`/retro`**，追问「什么能提前防住这个 bug」；如果真正的结论是没有好的接缝（seam）可以锁住它，那是 **`/improve-codebase-architecture`** 的活。

- **一大团迷雾般的工作：绿地项目或超大功能，一个会话装不下** → **`/wayfinder`**，这里认知负担最重的流程。当从这里到目的地的路还看不见时，它在 issue tracker 上画一张**共享地图**，由**决策工单**组成，一次解决一个，产出**决策而非交付物**，直到迷雾退去、路清楚了。**`/grill-with-docs`** 磨的是你能在一个会话里握住的想法，wayfinder 磨的是握不住的那种；它更慢、更密，所以只留给正好这样的情形，绝不要用在范围清晰的功能上。

  地图清晰后，**它交棒，不建造**：在 **`/to-spec`** 处并入主流程 —— 它把地图里互链的决策压成可构建的计划，然后照常 `/to-tickets` 与 `/implement`。把地图直接接进 `/implement` 会跳过这次压缩、丢掉互链的细节，所以只有在这件事其实很小的时候才直接去 `/implement`。

## 代码库健康

不是功能开发，只是维护。

- **`/improve-codebase-architecture`** 在你有空档时跑，让代码库保持适合 agent 在其中操作。它找出**加深机会（deepening opportunities）**；选中一个就**生成一个想法**，你可以带进主流程的 `/grill-with-docs`。它是找出候选者的勘察；**`/codebase-design`**（见下）是你设计所选者时用的工作台。

## 底层词汇

两份模型自动调用的参考，跑在其他 skill *之下*，各自是其词汇的唯一权威。当问题出在**词**而不是流程上时，直接取用它们；或者让上面的 skill 把它们拉进来。

- **`/domain-modeling`**：磨利项目的*领域*语言：质疑模糊术语、拆解一词多用（"account" 同时干三件事）、把难以撤销的决策记录成 ADR。它是 `/grill-with-docs` 驱动的那门主动功夫，用来让 `GLOSSARY.md` 保持为干净的词表。
- **`/codebase-design`** 是深模块词汇（module、interface、depth、seam、adapter、leverage、locality），用于设计模块的*形状*：在一个干净接缝上，用一个小接口罩住大量行为。`/tdd` 和 `/improve-codebase-architecture` 都说这套话。

## 阶段边界

**阶段（phase）** 是会话里的一块工作：访谈、实现、QA。在两个阶段的**边界**上你有五个选项，在它们之间做选择是整张地图里最模糊的决策：

- **Continue（继续）**：原地不动。不花成本，不丢东西。
- **`/clear`**：清空窗口，用于这里的一切对下一步都无所谓时。
- **`/handoff`** 写一份可携带的 markdown 文件。范围很窄：只用于**换 harness**、**换目录**、**交给同事**，或在阶段**中途**分叉出一个支线任务。它买到的是可携带性。
- **Subagent**：把范围紧窄的任务送进它自己的窗口，拿回一份报告。
- **`/compact`**：压缩当前上下文并用它给新会话播种。这是**默认**，位于决策树的底部而不是第一手选择。

读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 看有序决策树：五个问题、每个分支背后的推理，以及为什么一手来源的代价让 **Continue** 成为最该先排除的那个。要在边界**上**做决定；阶段中途就继续，或者把剩下的拆给 subagent。

## 独立技能

完全脱离主流程。

- **`/grill-me`**：与 `/grill-with-docs` 同样不留情面的访谈，但**无状态**：不在本地保存任何东西，也不建 `GLOSSARY.md`。当你**不在某个工作目录里**时用它（磨一份计划、一个设计、一篇文字，任何底下没有仓库的东西）。如果你在工作目录里，就用 `/grill-with-docs`：同一场访谈，还留下纸面痕迹，所以它严格更好。
- **`/grilling`** 是访谈原语本身：轮次、前沿、事实是 agent 的活、决策是你的活。`/grill-me` 和 `/grill-with-docs` 是两个具名入口，`/triage`、`/wayfinder`、`/improve-codebase-architecture` 内部都跑它。只有你想要不带包装的访谈时才直接取用。
- **`/prototype`** 是一个小而一次性的程序，用来回答一个设计问题：这个状态模型感觉对吗，或者这个 UI 该长什么样。一次性是对代码写法的约束，不是要销毁它的承诺：答案会折进真正的代码，而原型本身作为**一手来源**保存在从 main 切出的 `prototype/<name>` 分支上，由实现侧 issue 指向它。它是主流程第 2 步里的绕道，但任何时候一个设计问题在纸面上难以定夺，都可以取用它。
- **`/research`**：把阅读的粗活委托给**后台 agent**：它对着**一手来源**调查一个问题，然后在仓库里留下一份带引用的 markdown 文件。你继续干活，它去读。它产出的文件可以带进主流程的 `/grill-with-docs`，因为研究是喂思考，而不是替代思考。
- **`/to-questionnaire`** 用于卡住你的东西既不在你脑子里、也不在代码库里，而在**别人**那里时 —— 它写一份问卷让对方填。它是 `/grill-me` 的反面：不去访谈你关于主题的想法，而是访谈你关于**这次发送**的想法（发给谁、要拿回什么），把问题瞄准那个缺口。回来的东西是 `/grill-with-docs` 或 `/to-spec` 的原料。
- **`/wizard`** 是给只有**人**能做的步骤用的：开通基础设施、配置凭证或 CI secrets、在一个陌生的第三方后台里点来点去、跑一次性迁移或切换。它生成一个交互式 bash 脚本，逐个打开网址、逐个捕获取值，并写进 `.env` 和 GitHub secrets，于是这套流程不必再由你每次向 agent 重新解释。它是模型自动调用的，所以 agent 一撞上只有你能过的墙就会取用它。agent 自己能做的事就该自己做；这个技能只用于人真正在环里的场合。
- **`/wait-what`** 是给「没落地」的消息用的纠正器。在对话中途、在任意其他 skill 内部都能用，agent 会用你缺的上下文、用平实语言、用 `GLOSSARY.md` 的词汇把那句话重讲一遍。它是事后补救；`/grill-with-docs` 是事前良药，因为早先商定的共同语言才是阻止术语凭空掉下来的东西。
- **`/teach`**：跨多个会话学一个概念，把当前目录当成有状态的工作区。
- **`/writing-for-agents`** 是「写给 agent 读的文档」的参考：skill、AGENTS.md、被指向的文档。
