# 安卓发布与更新检查

## Problem Statement

现在改完代码只能在本机的模拟器上用开发宿主看效果。要把练练装到别的手机上，得在 Mac 上手动打包、
再想办法把文件传过去；既没有固定的下载地址，也不知道哪一份是正式产物。

装到手机上的包更是死路一条：以后改了代码，手机上那个旧版本不会知道有新版本，只能卸载重装，
而卸载会连本地库和照片一起丢掉。

## Solution

两件事，合起来让「改完 → 装到手机上 → 用上新的」变成一条可重复的路径：

1. **手动触发一次云端构建**：我在本地敲一条命令，GitHub 在云端编译出正式签名的安卓 APK，挂到这个
   仓库的 Release 上。推送代码不会触发构建，只有我主动下令才会。
2. **应用内检查更新**：练练启动时去 Release 看一眼版本号。有新版本就在今日页顶部出一条提示，
   点「去下载」跳到 APK 下载地址，由系统安装器覆盖安装；选择「以后再说」则这个版本不再打扰，
   直到下一个版本出现。

## User Stories

1. 作为一名开发者，我只在需要发版时触发构建，这样日常推送不会白白消耗 CI。
2. 作为一名开发者，我用一条本地命令就能触发构建并拿到产物，不必打开 GitHub 网页点来点去。
3. 作为一名开发者，我能从 Release 页面直接下载到可安装的 APK，这样换手机或发给别人时不用再找文件。
4. 作为一名开发者，我希望能先跑一次不发布的构建来验证流水线，这样第一次配置时不会在 Release 上留下废包。
5. 作为一名开发者，我希望正式包有固定签名，这样后续版本能覆盖安装、本地数据不会丢。
6. 作为一名开发者，我希望版本号只有一个真源，这样 tag、APK 版本和更新清单不会互相矛盾。
7. 作为一名开发者，我希望构建号自动递增，这样安卓安装器不会因为版本号不涨而拒绝覆盖安装。
8. 作为一名开发者，当构建失败时，我希望能看到是哪一步失败（依赖、签名、打包还是上传），而不是一个笼统的红叉。
9. 作为练练的用户，我打开应用时它会自己看一眼有没有新版本，不需要我主动去找。
10. 作为练练的用户，我看到「有新版本」时能知道是哪个版本、大概改了什么。
11. 作为练练的用户，我点一下就能去下载，不用自己复制版本号、翻仓库、找正确的 APK。
12. 作为练练的用户，我不想要更新时能明确说「以后再说」，并且它不会每次打开都再问我一遍。
13. 作为练练的用户，我在离线或 GitHub 访问不了的时候照常使用应用，不被打扰也不卡在启动。
14. 作为练练的用户，覆盖安装之后我的档案、判定、计划和打卡记录都还在。
15. 作为练练的用户，我能看出这次更新需要我自己确认安装，而不是以为它会悄悄在后台完成。
16. 作为一名维护者，我希望更新来源被签名保护，这样下载到的清单不是谁都能改的。
17. 作为一名维护者，我希望更新清单里只接受本应用的 id 和更高的版本，这样旧清单不会把应用降级。

## Implementation Decisions

**触发与流水线**

- 用 GitHub Actions，触发条件只有 `workflow_dispatch`；不在 `push` 上挂构建。
- 本地封装一条命令：触发 → 等待 → 下载产物。参数是更新说明，其余从仓库读。
- 触发输入包含一个「只构建、不发布」的开关，用于首次验证流水线。
- 版本号的唯一真源是应用配置里的 `version`（semver）；Release 的 tag 就是 `v<version>`，
  已存在则构建失败并提示先改版本，不允许静默覆盖。
- 构建号（安卓 versionCode）取 CI 的运行序号，保证单调递增，不需要人维护。
- 构建环境固定住工具链版本：nsh、NDK、platform、build-tools 与仓库现有文档一致，
  避免云端和本地产出不同。
- 依赖缓存：缓存 cargo 的注册表与构建目录，首次全量、之后增量。
- 产物两处：Release 资产（长期、直链、应用要用的就是它）和 workflow artifact（临时、便于排错）。

**签名与密钥**

- APK 用正式 keystore 签名，别名与密码来自仓库 Secret；keystore 以 base64 存 Secret，构建时落到临时文件。
- 更新清单用 Ed25519 密钥签名，公钥写进应用配置的 `updater`，私钥只存在于 Secret。
- keystore 和更新私钥都不进仓库；keystore 必须离线备份——丢了就无法再覆盖升级。

**更新来源**

- 应用配置的 `updater` 指向本仓库的 GitHub Release，并带上更新清单公钥。
- 每次发版在 Release 里同时挂 APK、`latest.json` 和它的签名文件。
- 清单由 nsh 的清单生成命令产出；安卓端的「去哪里下载」用一条显式链接指到本次的 APK 资产。

**应用内检查**

- 用 nsh 自带的更新模块，不自己调 GitHub API：它已经做了签名校验、app id 校验、只接受更高版本、
  只走 HTTPS、校验体积与 SHA-256。
- 检查发生在应用启动后、档案读出来之后，每次启动最多一次；失败（离线、限流、清单异常）完全静默。
- 开发运行（`nsh run`）与头less 测试里检查恒为空，因此界面上不会出现提示；这一点决定了验收必须用
  打包出来的 APK。
- 顶部提示条放在今日页最上方、页面标题之前；内容是「新版本 x.y.z」加一行从更新说明里取值而来的摘要；
  两个动作：「去下载」与「以后再说」。
- 「以后再说」按版本号记在本机设置里；同一版本不再提示，出现更高版本时重新提示。
- 安卓上 `canInstall` 恒为 false，因此「后台下载 + 自动安装」不在实现范围内；点「去下载」只做
  「打开下载地址」，由浏览器下载、系统安装器弹窗确认。
- APK 下载地址用 HTTPS 直链；应用不尝试自己在内部启动安装器。

**测试接缝**

- 更新检查的结果通过一个可注入的来源进入界面：生产代码在启动时调用 nsh 的更新模块，测试通过既有的
  测试入口注入「有一个可用更新」。
- 注入走已有的 `Testing` 测试入口（`Testing.reset()` 所在的那一层），不引入第二套测试开关。
- 断言只落在用户看得见的行为上：提示条出现、文案含版本号、点「以后再说」后消失、重开不再出现、
  出现更高版本时重新出现。

## Testing Decisions

好测试的标准：只断言用户能在屏幕上看到什么、点完之后看到什么，不断言内部信号名、不依赖具体实现结构。

- 头less 界面测试（`nsh test`）：在今日页注入一个可用更新，验证提示条渲染、版本号文案、两个按钮的
  点击结果，以及「以后再说」的跨重启持久化。参照现有的今日页与存储测试写法，用同一个测试入口清库。
- 本机设置层：验证「跳过的版本」写入后能读回、能被更高版本顶掉。参照设置的既有单测。
- 云端构建：无法在仓库内自动断言，采用可执行的手工验收——先跑一次「只构建不发布」，确认 APK 产出；
  再正式发布一次，确认 Release 上有 APK 与更新清单，且 APK 能在手机上覆盖安装。
- 端到端验收：用较低的版本号打一个包装到模拟器，发布一个更高版本，确认应用能发现、能跳到下载、
  覆盖安装后本地数据仍在。

## Out of Scope

- OTA（只更新 TSX 代码、不换 APK 的通道）。
- iOS 与桌面平台的更新。
- 在应用内部下载 APK 并直接拉起安装器（需要安卓原生壳，且仍然需要用户确认）。
- Google Play 商店分发与 AAB 上传。
- 增量更新、差分包、灰度发布、强制更新、回滚。
- 自动清理旧 Release 资产。

## Further Notes

- 正式包与开发包的签名不同，把正式 APK 装到装有开发包的设备上会报签名冲突，必须先卸载；卸载会清空本地库。
- 用户第一次从浏览器安装时，需要在系统设置里允许该浏览器「安装未知应用」。
- GitHub 未认证 API 有每小时 60 次的限制；每次启动检查一次远低于该阈值，但不能放进循环。
- 应用 id 已固定，任何版本都必须保持一致，否则系统视为另一个应用、无法覆盖升级。
- nsh 的版本需要与仓库文档保持一致；升级 nsh 会改变内嵌运行时，属于需要重新发布整包的变化。
