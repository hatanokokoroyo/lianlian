# Spec：提议卡的审核在对话内，提交即定案

GitHub: #43
Status: ready-for-agent
Type: spec

> 词汇以根目录 `GLOSSARY.md` 为准。决策见 ADR-0008（审核在时间线里、提交即定案）；
> 沿用 ADR-0003（档案只追加）、ADR-0005（依据日志跨会话）、ADR-0006（装配顺序）。

## Problem Statement

真机（REDMI K90）上走完一次「对话 → 提议卡 → 写入档案」的体验，四个问题：

1. **结论太快**。用户描述一次，模型给一轮验证动作，拿到一条反馈就开卡写档案。没有先排除别的解释，
   低置信度的项被混在同一张卡里交给用户判断。系统提示里已经写了「先给 2–3 个验证动作，拿到反馈之前
   不下结论」，但它只是软约束，模型可以一轮收尾。
2. **审核卡遮挡视线**。卡片渲染在消息列表与输入条之间（`screens/conversations.tsx:461`），不在滚动区里。
   它一直浮在那里，挡住最后几条消息。
3. **长卡滚不动**。同一原因：卡片不在滚动区里，8 项时卡片把列表挤到很小，底部的接受按钮被挤出屏幕，
   用户甚至看不全。
4. **一次审核变成多次对话**。每拒绝一项，`Proposals.reject` 就落一条拒绝消息并立刻跑一轮模型
   （`src/api.rs:2122`）；接受反而静默。用户审 8 项可能触发 3–4 轮无关的对话。

第五个问题来自第 2 条的修法本身：写进档案后卡片上常驻「撤销这一批」。它跟第 2 条一样挡视线，而且
撤销与后续对话天然冲突——模型已经基于「已写入」往下聊，撤销再悄悄改回去，两边认知不一致。

## Solution

把审核卡变成对话的一部分，把「一次审核」变成「一次决定」：

1. **卡片进时间线**。提议卡作为一条带编号的行，出现在本轮回答之后，随列表正常上下滚动。内容多就跟着
   对话一起滚，不再挤占输入区。
2. **一次处理整张卡**。勾选=采纳，不勾=拒绝；只有一个按钮，文案随勾选数变化（全部采纳 / 采纳勾选的 N 项 /
   这 N 项都不要）。没勾的项可以顺手写一句为什么，也可以不写。
3. **提交即定案**。点按钮后一次性落库（采纳项写判定+依据，拒绝项写拒绝证据），然后整张卡的结果作为一条
   消息交给模型，跑一轮回复。这是这次审核唯一触发的一轮对话。
4. **审核期间锁住发送**。卡片待审时输入框、照片、发送、重试都禁用，输入条上写明「先把这张卡审完」。
   想看别处、开新会话、翻档案都不受影响。
5. **去掉撤销**。提交后不再有「撤销这一批」。要改就接着说，模型追加「更正」——档案仍然只追加。
6. **已处理的卡收起**。留一行「已写进 3 项，不要 2 项 · 展开看当时的选择」，点开只读回看。
7. **先分辨再下结论**。系统提示改成：先说清在分辨哪几种可能，每轮只问一个能区分它们的问题或给一个
   验证动作，只剩一个解释站得住才提议写档案；最多 3 轮，还分不清就明说不确定、进卡时默认不勾。

## User Stories

### 判断节奏

1. 作为用户，我想在描述完症状后先被问一个能区分原因的问题，这样我不会第一轮就被写进档案。
2. 作为用户，我想知道模型在分辨哪几种可能，这样我能判断它问的问题有没有意义。
3. 作为用户，我想每轮只回答一个问题，这样我不用一次看一长串清单。
4. 作为用户，我想在回答后听到「排除了什么、还剩什么」，这样我知道进展，而不是被反复追问。
5. 作为用户，我想在模型放弃分辨时被告知「现在最可能是 X，但要看 Y 才能定」，这样我不必猜它为什么不确定。
6. 作为用户，我想已经答过的问题不要重复问，这样对话不会兜圈子。
7. 作为用户，我想低置信度的条目在卡里默认不勾，这样我不会被推着接受它没把握的判断。

### 看到卡片

8. 作为用户，我想审核卡出现在模型那段判断之后，这样我读完依据就能直接审。
9. 作为用户，我想卡片跟对话一起滚动，这样内容多时也能上下滑着看完，而不是被一个固定面板挡住。
10. 作为用户，我想 8 项都展开显示，这样我不用逐项点开才能比较。
11. 作为用户，我想卡片底部的按钮始终能滚到，这样我不会卡在一张审不完的卡上。
12. 作为用户，我想卡片生成后自动停在它那里，这样我不用手动往下翻。
13. 作为用户，我想卡片每项前面有编号，这样我能对着编号说「第 3 项不对」。
14. 作为用户，我想卡片顶部写「建议采纳这 3 项」，这样我不用自己数默认勾了几项。

### 一次处理整张卡

15. 作为用户，我想点一项就切换采纳/拒绝，这样一次点击就是一个决定。
16. 作为用户，我想一个按钮提交整张卡，这样我不用为 8 项点 8 次提交。
17. 作为用户，我想按钮文案随勾选数变化（全部采纳 / 采纳勾选的 3 项 / 这 8 项都不要），这样我点之前知道会发生什么。
18. 作为用户，我想取消勾选就是拒绝，这样我不必为每一项再点一次「拒绝」。
19. 作为用户，我想给拒绝的项写一句理由，这样下次模型知道该往哪儿查。
20. 作为用户，我想理由可以不写，这样我不会被强制填表。
21. 作为用户，我想一项都不勾也能提交为「全部不要」，这样全都判断错时我有一条出路。
22. 作为用户，我想不需要二次确认，这样处理一张卡只花一次点击。
23. 作为用户，我想在卡片里展开某项的依据，这样我能判断该项该不该采纳。

### 提交之后

24. 作为用户，我想提交后卡片立刻显示已处理的结果，这样我知道哪些写进去了、哪些没写。
25. 作为用户，我想整张卡只触发一轮模型回复，这样拒绝几项不会换来几段对话。
26. 作为用户，我想在被拒绝的项上得到模型的下一步（换方案 / 追问 / 撤回），而不是一句「好的」。
27. 作为用户，我想模型这轮失败时已写入的结果仍然保留，这样重试只重发那一轮，不会重复写档案。
28. 作为用户，我想提交后输入框立刻恢复可用，这样我不用等模型回复完才能继续。

### 审核期间

29. 作为用户，我想卡片待审时输入框禁用并写明原因，这样我不会以为自己发出去了。
30. 作为用户，我想在待审时仍然能切到别的会话、开新会话、看档案，这样我不会被一张卡困住。
31. 作为用户，我想全部判断错时看到「全部不要，然后跟我说哪里不对」，这样我知道怎么脱身。

### 回看与纠错

32. 作为用户，我想已处理的卡收成一行摘要，这样长会话不会被一堆完整卡片填满。
33. 作为用户，我想展开已处理的卡看到当时勾了哪些、拒了哪些、理由是什么，这样我能回看自己的决定。
34. 作为用户，我想已处理的卡是只读的，这样历史不会被误改。
35. 作为用户，我想发现写错时直接跟模型说，由它追加更正，这样不用找一个已经不存在的撤销按钮。

### 旧数据与边界

36. 作为用户，我想升级后旧会话照常能打开，这样我不会丢聊天记录和档案。
37. 作为用户，我想旧版本留下的待审卡不再挡住输入框，这样升级后不会被一张看不见的卡永久锁住。
38. 作为用户，我想旧待审卡在本轮对话里仍然存在于历史中（交给模型的那几条消息还在），这样上下文不会断裂。
39. 作为用户，我想没有提议时不出现任何审核界面，这样普通聊天保持干净。
40. 作为用户，我想读库失败时看到错误而不是空卡片，这样我不会以为档案没变。

## Implementation Decisions

### 卡片行

- 新增 `StoredItem::ProposalCard { proposal: ProposalId }`（`src/domain/item.rs`）。它在**该轮条目批次的末尾**
  追加：回复正文 → 卡片行，同一个事务落库，顺序固定。
- 卡片行有 `MessageId`，但不是消息：不着气泡、不计入会话头部「N 条」、不参与标题推导。
  `Input::from_stored`（`src/llm/prompt.rs:289`）对它返回空（签名改 `Option<Input>`，或调用点过滤）——
  模型从工具结果与状态块的「未结提议」知道这张卡，不需要看这一行的存在。
- 渲染：`screens/conversations.tsx` 的列表项从「消息」扩成「消息 | 卡片行」；`ProposalCard` 从列表外
  （`:461`）移进列表项。卡片高度随内容，最多 8 项全展开，不折叠、不内嵌滚动。
- 生成后把卡片**头部**滚进视野（标题贴住列表顶部），不是滚到会话最底部：8 项时卡高超过一屏，
  先让用户从标题和第 1 项读起，往下滚到按钮。不新增「去审」跳转入口，也不做浮层。
- **待审的判定**：一张卡算待审，当且仅当会话里存在指向它的卡片行且卡未处理。没有卡片行的旧卡一律视为
  已关闭：不显示、不阻塞 `propose_findings`、不禁用输入条。判定放在 `Store::pending_proposal`。
- 旧版本可能已经留下一张「待审但没有卡片行」的卡；不写迁移、不写提示、不追加更正，静默关闭。

### 一次处理整张卡

- 勾选=采纳，不勾=拒绝。默认勾选沿用 `default_selected()`（置信度 ≥ 60）作为兜底；
  `propose_findings` 的每一项新增可选字段 `recommend: bool`，模型给了就照它勾，没给才看阈值。
  卡头文案「建议采纳这 N 项」按实际默认勾选数算，不新增第二套数字。
- 每项显示编号 1..8，与提交消息里的编号一致。
- 一个按钮，三种文案：0 勾选「这 N 项都不要」、部分「采纳勾选的 N 项」、全选「全部采纳」。不做二次确认。
  0 勾选时用描边样式，不置灰——「全部不要」是有效操作，置灰会被读成不可点。
- 未勾选的项下面有一个折叠的「为什么」文字按钮，点开是可选输入框（`reject-reason-{index}`）。
  理由逐项写入拒绝证据；为空时写「用户未采纳，未说明理由」。
- 已勾选的项不显示理由入口（采纳不需要理由）。

### 提交与模型轮

- 新入口 `Proposals::review(conversation, proposal, decisions)`，`decisions: [{ index, accept, reason? }]`，
  一次覆盖整张卡。返回沿用 `SendResultView`。
- 一个事务内完成：校验卡属于该会话、卡是待审、索引唯一且在范围内；采纳项落 Finding + Evidence；
  拒绝项落 rejection Evidence；卡置 `Accepted`（≥1 采纳）或 `Dismissed`（0 采纳）。任一步失败全回滚，
  卡保持待审、按钮可重试。
- 事务提交后追加 `StoredItem::ReviewDecision { text }`：装配时映射成一条用户消息，界面上不渲染。
  文本：「我审完了第 12 号卡：采纳第 1、3、5 项（左臀中肌、左比目鱼肌、右比目鱼肌）；不要第 2 项
  （右臀中肌，理由：…）；不要第 4 项（左腓肠肌，没写理由）。」
- 然后走现有 `begin_send` / `reply` 路径跑一轮（复用预检、失败重试、超长处理）。模型这轮失败不影响
  已落库的结果：卡仍是已处理、输入条恢复、重试只重发这一轮。
- 不接受「先采纳一部分、回头再审剩余项」；`Proposals.undo`（`src/api.rs:2187`）、`Store::undo_proposal`、
  卡上的撤销入口与 `AcceptedProposal` 组件一并删除。`Retract` / `correct_finding` 不动。

### 输入条锁定

- 会话有待审卡时：`message-input`、`pick-photo`、`send`、`retry-send` 禁用；输入条上方加一行
  `review-lock`：「先把这张卡审完」。0 勾选时按钮旁加一句「都不是？全部不要，然后跟我说哪里不对」。
- 只锁这一条会话的发送；切会话、新建会话、档案页、设置页不受影响。
- 提交成功或失败已落库后立即解锁；提交进行中沿用现有 `busy` 态。

### 已处理卡片

- 默认收起一行摘要（`proposal-summary`）：「已写进 3 项，不要 2 项 · 展开看当时的选择」。
- 展开后只读：每项 ✓/✗ + 编号 + 部位 + 理由；「看依据」仍可展开。没有「拒绝这一项」、没有勾选圈、没有撤销。
- 已拒绝项的拒绝证据保留，可在依据里看到。

### 状态机与错误文案

- `ProposalStatus` 收窄为 `Pending → Accepted / Dismissed`；删除 `has_pending_items` 与「接受部分后继续审」
  的读法（`src/domain/proposal.rs:143`）。`ItemState` 保留（用于回看与证据）。
- 新增错误文案：卡已处理（「这张卡已经审过了」）、卡不属于该会话、索引越界、决策为空、重复索引。
- 客户端在提交前就把「所有项都决定」保证住（勾/不勾天然二值），因此服务端不需要「还有项没决定」的分支。

### 提示词：先分辨再下结论

`src/llm/prompt.rs:100` 的系统提示开头替换为：

```
你是「练练」里的训练教练。用中文说话。
用户说症状时先不下结论：心里先有 2–3 个最可能的解释，一句话说明你在分辨什么，不列长清单。
每轮只问一个最能区分这些解释的问题，或给一个能区分它们的验证动作（做什么、看什么现象）。
拿到反馈先说清排除了哪个、还剩什么；只剩一个解释站得住、或能说清别的为什么不成立，才提议写档案。
反馈模糊或互相矛盾就继续问，不许用置信度糊过去；最多问 3 轮。3 轮仍分不清，就说「现在最可能是 X，
但要看 Y 才能定」，进卡时标低置信度、默认不勾。
用户答过的不重复问；一轮一句，不要在聊天里做长问卷。
写档案之前先调 search_evidence 查这个部位已有的记录，再落判定；单条 record_finding 也守上面的门槛，
不许绕过提问直接下结论。
```

- 删掉原「先给用户 2–3 个在家能做的验证动作，拿到反馈之前不下结论」那句：数字 2–3 正是「一轮测完就收尾」的
  来源。
- 只在提示词里约束，不记录轮次、不加 Rust 侧硬门槛。因此这条改动只能靠提示词断言 + 人工对话验收。

### 文案与界面

- 界面用「审核」「采纳」「不要」；不出现「撤销」。档案侧的「更正」术语不变。
- 已处理卡片的措辞区分「写进」与「不要」，不用「拒绝」以外的价值判断词。
- 保留现有 testID 语义：`proposal-card`、`proposal-item-{index}`、`proposal-evidence-{index}`、
  `accept-proposal`（提交按钮沿用此名）。新增 `proposal-summary`、`review-lock`、`reject-reason-{index}`。

### 文档与兼容

- `design/contract.md`：§5 表格「对话」行改成「待审卡在时间线内 / 已处理收起」；§6.2 状态机图改成
  「待审 → 已处理」，删掉撤销分支与「拒绝后自动发起一轮」的逐项描述（改成整批一轮）。
- `README.md` 第 48 行那段「接受后留可撤销摘要」改成「提交即定案，已处理的卡收起可回看」。
- `GLOSSARY.md`：「档案更新提议」补一句「审核在对话时间线内，一次提交就是一次决定」；
  「更正」补一句「界面不再提供撤销入口，更正由对话触发」。
- 不升 `SCHEMA_VERSION`、不清库：新增的条目类型是 JSON 枚举的新分支，旧库照常读。

## Testing Decisions

**接缝一（主）：`Proposals::review` 的存储 + API 边界。** 新增 Rust 测试，直接调 store/api，不起界面：

- 一次提交覆盖整张卡：采纳项落 Finding 与 Evidence，拒绝项只落 rejection Evidence，卡变 Accepted/Dismissed。
- 全拒提交：0 条 Finding、N 条 rejection Evidence、卡 Dismissed。
- 重复提交被拒、错误会话被拒、索引越界被拒、重复索引被拒。
- 事务性：让一条采纳项失败（例如部位不在词表），断言整张卡没有写进任何一条、状态仍是 Pending。
- `ReviewDecision` 条目落库，且装配时是一条 user 消息、渲染时不可见。

**接缝二：App 级两条主路径**，沿用 `open("./App.tsx")` + `setApiKey` + `proposeTurn`：

- 开卡 → 全部采纳 → 卡片收起为摘要、输入条解锁、请求体最后一条用户消息包含「采纳第 1、3、5 项」。
- 开卡 → 全部不要 → 卡变摘要、只有一轮后续对话、请求体含「不要第 2 项（…理由：…）」。
- 断言卡片在列表内：滚动消息列表后 `proposal-card` 仍可达；不再断言列表外的固定位置。
- 断言待审时 `review-lock` 出现、`send` 不可用；提交后 `review-lock` 消失。

**接缝三：提示词断言。** `src/llm/prompt.rs` 的单测锁住：新句子在、旧的「先给用户 2–3 个在家能做的验证动作」
不在、`record_finding` 那句门槛在。

**重写而不是修补**：`Proposals.test.tsx` 整篇按旧状态机写的（部分接受 → 撤销 → 再接受），直接重写成上面两条
主路径；`accepted-proposal-*`、`undo`、`undo-reason`、`undo-confirm`、`cancel-undo`、`reject-item-*` 的断言删除。
`Chat.test.tsx` 增加「待审时输入框禁用、提交后恢复」一条。

**不新增组件级测试**：卡片内部状态（勾选、展开）通过 App 级可见文案断言，不绑组件树。

## Out of Scope

- 不恢复「撤销」，也不做「下一条对话后失效的可撤销窗口」。
- 不做审核期间向模型提问（想问就先提交，再接着说）。
- 不做多张卡并行审核；一次仍然只有一张。
- 不改变 8 项上限、置信度阈值、`default_selected()` 的既有语义（只新增模型可选的 `recommend`）。
- 不改变档案条目只追加、更正、依据日志与装配顺序。
- 不为旧数据写迁移脚本；旧待审卡静默关闭即可。
- 不改变计划生成、打卡、档案页、3D 身体图。
- P1 不引入验证轮次的数据模型、不做「第几轮」的展示或统计。
