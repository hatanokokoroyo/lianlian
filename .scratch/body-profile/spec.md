# Spec：身体档案与锻炼计划（MVP）

> 词汇以仓库根 `GLOSSARY.md` 为准；本文出现的每个术语都在词表里。决策以 `docs/adr/0001`–`0006` 为准。

## Problem Statement

我身体有具体的问题——蹲不下去、抬臀时左臀先酸、久坐后腰紧——但我不知道根因在哪，也不知道每天该练什么。看视频、问朋友、记在备忘录里，都没法沉淀：三个月后我记不起当时判断的是什么，也看不出到底有没有变好。请教练太贵，而且我真正需要的不是"再给我一套动作"，而是**有人记得我的身体是什么样的**，每次都基于这个认识跟我说话。

## Solution

手机上一个纯本地 app（无账号、无后端，模型 key 我自己填）：

1. 我填身体基本属性（年龄/性别/身高体重/基础疾病）和训练条件（每周能练多久、在哪练、有什么器械）。
2. 我跟 agent 对话，可以拍照。它会给我验证方案（"单腿站立 30 秒，看髋会不会掉"），我照着做并反馈，它据此在**档案**上写下某一个部位（精确到肌肉或骨骼）的判定，并留下一段**依据日志**（我原话说了什么、验证反馈、它的推理）。
3. 我随时可以开新会话问别的事——它不记得上一个会话的原文，但它能查到那些第一手细节，不会只看到"距骨受限"这种结论。
4. 它据此给我一份**计划**（臀桥 3×10、蚌式开合 3×10、死虫式 3×10），带频次规则和复查日。
5. 我每天打开 app 就是今天的动作清单，边练边勾；全部勾完就是**打卡**。有事可以整天**推迟**到下一个空档日，或**跳过**某个动作。
6. 月历上我看见自己练了哪些天、漏了哪些天；点进某天能看到当时到底练了什么。

## User Stories

1. 作为用户，我想在第一次打开时就被引导填完年龄/性别/身高体重，这样 agent 有最基本的判断依据。
2. 作为用户，我想随时修改基本属性，这样我胖了瘦了、确诊了新的基础疾病时档案不会过期。
3. 作为用户，我想每次记录体重时都留一条带时间的**测量**，这样我能在折线图上看到变动，而不是只看到最新一个数字。
4. 作为用户，我想删除一条填错的测量，这样折线图不会被我手误的 999 公斤污染。
5. 作为用户，我想填每周能练几天、每次多久、在哪练、有什么器械，这样计划不会给我安排一个我根本做不到的方案。
6. 作为用户，我想在没填训练条件时被 agent 追问而不是被硬塞计划，这样我不用事后自己把那套动作改成能做得了的样子。
7. 作为用户，我想开一个新会话随便聊，这样我不必先想"这属于哪个话题"。
8. 作为用户，我想在同一个会话里连续追问（"那再慢一点"），这样对话是连贯的而不是每次重新解释。
9. 作为用户，我想拍照给它看（体态、疼痛位置），这样它不必靠我笨拙地描述。
10. 作为用户，我想让它先给我一个可执行的验证方案（做什么动作、看什么现象），而不是直接下结论，这样我对这个判定是可信服的。
11. 作为用户，我想看到它对某个部位的判定具体是什么（张力弱/紧、左弱/右弱、活动度受限、疼痛、稳定性），这样"你臀弱"这种模糊说法不会出现在档案里。
12. 作为用户，我想在一个卡片里一次审完它这轮想改的所有部位（可逐项勾选、可展开看依据），这样它不会一条一条打断我。
13. 作为用户，我想拒绝它的一条判定，并且在拒绝时可以选择补充说明（"不是臀部，是我膝盖疼"），这样拒绝本身也在推进对话。
14. 作为用户，我想在拒绝之后立刻得到它的下一步（换方案/追问/撤回并说明），而不是一句"好的，已记录"。
15. 作为用户，我想在它一次想改 8 项以上时被告知需要分轮，这样我不会面对一张审不完的清单。
16. 作为用户，我想看到每个部位判定下面的**依据**（我当时的原话、验证反馈、它的推理），这样我能判断这条判定靠不靠谱。
17. 作为用户，我想在档案里看到每个部位当前的状态，以及它是**什么时候、因为什么**变成这样的，这样我能回顾变化。
18. 作为用户，我想看到某个部位的历史时间线（几次判定、各自的依据、哪次被更正过），这样"三个月前说臀弱，现在好了吗"有答案。
19. 作为用户，我想把一个已经好了的部位标记为**已解决**（追加一条正常判定），这样档案反映现状而不必删历史。
20. 作为用户，我想撤回一条当时就判错的条目并写明错在哪，这样档案不会带着错误结论继续误导计划。
21. 作为用户，我想在档案里看到"左膝/右膝"这种左右区分，这样不对称的问题不会被抹平。
22. 作为用户，我想让 agent 只能记录词表里存在的部位，这样我不会看到"臀部肌肉"和"臀大肌"同时存在、互相矛盾的两条记录。
23. 作为用户，我想看到某个肌群的整体情况（由成员肌肉聚合而来），这样我不必自己把几条记录加总。
24. 作为用户，我想让它基于档案和训练条件生成一份计划，而不是给一份通用课表，这样我做的每个动作都有理由。
25. 作为用户，我想看到每个动作对应的是档案里哪条判定，这样我知道"为什么我要做臀桥"。
26. 作为用户，我想让计划告诉我频次规则（每周 3 次 / 每 2 天一次），由 app 展开成具体哪几天，这样我不必自己排日历。
27. 作为用户，我想把某一天整体挪到另一个日期，这样出差或加班不会让我直接断掉。
28. 作为用户，我想跳过某个今天做不了的动作（比如没有器械），这样它不会把整天卡在"未完成"。
29. 作为用户，我想在计划到期（复查日）时看到提示，这样我不会把一套两年前的方案一直做下去。
30. 作为用户，我想每天打开 app 直接看到今天的动作清单，这样我不需要先导航到某个地方。
31. 作为用户，我想逐项勾选动作，这样练到一半去接孩子回来还能接着勾。
32. 作为用户，我想在全部勾完时看到明确的打卡反馈，这样我知道今天这笔账结清了。
33. 作为用户，我想在月历上区分"已完成/计划中/已推迟/未完成/休息日"，这样我一眼看出这个月到底练了几天。
34. 作为用户，我想点月历里的某一天回看当天的动作与勾选情况，这样我能想起"那天到底练了什么"。
35. 作为用户，我想在月历上看见未来已排好的训练日，这样我能提前安排生活。
36. 作为用户，我想自己填 DeepSeek 的 key，这样我不必为别人的服务器付钱、身体数据也不出设备。
37. 作为用户，我想在网络断了或 key 失效时看到明确的、可操作的错误（重试 / 去设置），并且我打了一半的字和选好的照片不会丢。
38. 作为用户，我想在会话太长时被提示开新会话（并且新会话仍然记得我的身体情况），这样对话质量不会随长度下降。
39. 作为用户，我想在删除一个会话时，它的依据日志仍被保留（标注来源已删除），这样档案不会因为整理聊天记录而失忆。
40. 作为用户，我想看到本地数据的容量占用，这样我知道什么时候该归档。
41. 作为用户，我想在没有任何计划时被引导去完成首次评估，而不是看到一片空白。

## Implementation Decisions

**形态与分层**（ADR-0002）
- Rust + TSX 混合：Rust 拥有领域模型、存储、模型网关、照片；TSX 只做屏与交互，通过自动生成的类型化接口调用 Rust。
- Rust 侧分四个包内模块：`anatomy`（静态词表）、`domain`（纯函数，零 IO）、`store`（redb）、`llm`（网关 + 装配）；外加 `photos` 与 `api`（对 TSX 暴露的入口）。

**部位与状态**（ADR-0003、ADR-0004）
- 部位词表是随包编译的静态数据：80 块常用肌肉 + 40 块主要骨骼 + 20 个肌群，带中英/拉丁名、所属肌群、左右、`schema_version`；扩词表只加不删（Finding 引用部位 id）。
- 肌群不是可记录部位，是查询时聚合（成员取最差值）。
- 五轴取值全为枚举：张力（弱/正常/紧）、对称（左弱/右弱/对称）、活动度（受限/正常）、疼痛（无/有 + 0–10）、稳定性（差/正常）。加轴需新 ADR。
- 一条 Finding = 部位 + 若干轴的取值 + 置信度 + 证据引用 + 时间 + 来源提议；**只追加**。
- 修正走 Correction：**解决**（追加一条正常判定）与**撤回**（标记某条无效，必须写理由）是两种不同的 Correction，UI 上也分开展示。

**依据日志**（ADR-0005）
- 每次 Finding 变动写一条结构化日志，四段必填：用户说法要点 / 验证方案与反馈 / 推理 / 不确定之处。
- 日志默认不进装配，由 `search_evidence` 检索，`limit` 硬上限 20。
- 删除会话只删消息正文，日志与照片保留并标注来源已删除。
- `record_finding` / `correct_finding` 之前必须先对该部位 `search_evidence`；此约束由 Rust 工具层强制并返回错误让模型重试。

**装配**（ADR-0006）
- 顺序固定：`[系统提示][本会话历史（逐轮原封不动累加）][档案投影 + 训练条件 + 未结提议][本轮消息 + 照片]`。
- 跨会话不传别的会话的历史；状态记忆靠档案投影，情景记忆靠检索。
- 系统提示必须包含"当前状态在最后一条消息之前给出"这一句。
- 会话长度阈值：20 万 token 提示开新会话，50 万 token 强制新开（新会话自动带档案投影）。

**工具集**（共四个，宁少不多）
- `search_evidence({ site?, axis?, from?, to?, contains?, limit })`
- `record_finding(...)` —— 高置信度 + 用户同轮已口头确认时使用，落库后可撤销
- `correct_finding(...)` —— 解决 / 撤回
- `propose_findings(items[])` —— 低置信度或批量时使用，一次最多 8 项，生成待定提议
- 计划用 `generate_plan(...)`（第五个）：频次规则、动作清单、每个动作对应的 Finding、复查日。

**提议与撤销**
- 提议卡片：一项一行、默认勾选（低置信度默认不勾）、可展开依据、底部"接受选中 / 全部接受"。
- 接受 → 落 Finding；拒绝 → 落"用户拒绝 + 可选的理由"作为证据，不产生 Finding；拒绝后 agent 必须同轮给出下一步（换方案 / 追问 / 撤回并说明）。
- 直接写入的 Finding 在会话里留一条可撤销摘要；撤销 = 追加 Correction，不删除。

**计划与训练日**
- 同一时刻只有一个生效计划；计划有版本号，agent 调整 = 新版本。
- 计划展开成训练日时，**day 存的是动作快照**而不是指向计划版本的引用——否则改计划会篡改历史。
- 日状态四种：计划中 / 已完成 / 已推迟 / 未完成；自然日 00:00 断界；跨天未打卡自动落为未完成。
- 推迟只作用于整天（顺延到下一个空档训练日，可手动改到别的日期）；单动作走跳过。
- 复查日默认 4 周，到期在今日页顶部提示。

**存储**（ADR-0002）
- redb 单文件位于 app 私有目录；表：`meta`（schema 版本）、`basics`、`measurements`、`findings`、`corrections`、`conversations`、`messages`、`proposals`、`photos`、`plans`、`days`、`settings`。
- 照片存 app 私有目录的原图（长边 2048）+ 缩略图；`photos` 表只存元数据与路径。
- `measurements` 是唯一允许单条删除的数据。

**模型网关**（ADR-0001）
- 一个接口 + 一个 DeepSeek 实现（OpenAI 格式的 `/responses`，无状态、多轮自拼）；换后端只换实现。
- 流式输出优先；若 Android 上 SSE 实测不通，退化为分段返回 + "思考中"。

## Testing Decisions

**Seam（一个就够）**：Rust 的 `api/` 边界。TSX 只经由它拿数据、发命令；因此**所有自动化测试都落在它下面**，TSX 屏不写单测。

- `domain/` 纯函数（零 IO）——表驱动单测，这是测试的主战场：计划频次规则展开、日状态迁移（含推迟/跳过/跨天结算）、五轴取值校验、肌群聚合、Finding 投影（含更正后不再生效）。
- `store/` —— 用临时目录的真实 redb 文件做集成测试：区间查询、时间序列、动作快照不受计划变更影响、删除会话不动日志。
- `llm/` —— 假客户端 + 录制好的真实响应语料（不联网）。重点测**装配**：同一状态两次装配必须字节一致（缓存前缀稳定）；档案变化只影响尾部；跨会话不串历史。这条用"快照式"断言。
- `photos/` —— 平台依赖（系统 picker），不测；缩略图缩放算法可单测纯函数部分。
- 工具层的硬规则（未查不得写入）用假客户端驱动一次完整工具往返来测——这是本项目最值得钉死的一条不变量。
- 端到端只在最后用 `nsh test`（headless）跑一条"填属性 → 对话 → 接受提议 → 生成计划 → 勾选打卡"的主干，作为冒烟。

**好测试的标准**：只断言外部可观察的行为（档案怎么变、日历上哪几天、装配的字节），不断言内部函数调用次数；每条测试的名字用词表里的词（"打卡"而不是"完成所有项目"）。

## Out of Scope

- 账号、登录、多设备同步、任何后端服务。
- 2D/3D 解剖图展示（数据结构预留，视图不做）。
- 推送通知与提醒（能力已有，本期不做）。
- 导出/导入、备份、跨设备迁移。
- 多计划并存、计划交接、教练/他人共享。
- iOS、桌面端、Web 端。
- 自定义词表增删、用户自建部位。
- 语音输入（能力已有，本期不做）。
- 打卡动画（本期只做最简反馈）。
- 多语言（先中文单语）。

## Further Notes

- **最大的技术风险是第一步**：Rust + TSX 混合形态在 Android 上从零跑通（类型生成、native module 注册、真机/模拟器）。它必须是最早完成的工单，失败就退回纯 TSX + `Storage` 5 MB（ADR-0002 的备选路径，接口不变）。
- **第二风险是模型输出的不可预测**：建议在第一个对话工单里就固化一份"真实对话录制语料"，之后所有装配与工具测试都跑它，避免每次改提示词都靠手感。
- **`days` 存快照**、**日志不随会话删除**、**硬规则在工具层**——这三条最容易被后来者"优化"掉，也是它们各自 ADR 的写作原因。
- 词表需要人审：中文名与"这 80 块肌肉是不是你真正会练的"需要你过一遍，它决定 agent 能说什么话。
