# harness-era-talk · 宣讲件计划

> 状态：2026-11-20 起草，**结构待确认**。本文件是跨机器继续工作的计划底稿，不是最终文案。
>
> 目的：给研发同事和非研发领导讲清楚，matt 工作流 + OpenDesign 如何改变 AI 工程的工作方式与效率。
>
> 受众：不熟练 AI 开发的研发同事；不懂研发但关心投入产出的领导。
>
> 交付：`design/harness-era-talk/` 下的 `deck.html`（16:9 演讲模式）、`read.html`（纵向阅读模式）、`notes.md`（讲稿、来源、截图说明）。三份读同一份内容，不维护两套文案。

## 一句话主张

AI 工程的效率提升，不是让 AI 多写代码，而是把人从重复解释、丢上下文和任务切换里解放出来，把注意力留给决策。

## 待确认的 8 个决策

1. **项目落点**：仓库 `design/harness-era-talk/` 为真源 + OpenDesign 预览，还是只放 OpenDesign？
   - 推荐：仓库为真源，OpenDesign 只做预览/批注。
2. **受众策略**：一份 deck 两层读法，还是工程版/管理版两份？
   - 推荐：一份，每章底部加「给管理的一句话」。
3. **叙事主线**：开篇立坐标系 → Part 1 缺位 → Part 2 补齐；约 33 页。
   - 推荐：按本文件结构。
4. **Part 1 缺口**：五个（说不清/记不住/装不下/验不了/看不见），还是三个 + 一个？
   - 推荐：五个；第五个「看不见」是 OpenDesign 的入口。
5. **案例**：两段案例（A 视觉方向三次提交；B 档案 IA 文档链路），还是只用一个 feature？
   - 推荐：两段；A 讲速度，B 讲准确与落地。
6. **驾驭工程配图**：hero 插画 + 控制塔信息图，还是只要一张？
   - 推荐：两张；hero 负责情绪，信息图负责论证。
7. **Part 3 与 wayfinder**：先占位、暂不建 GitHub 决策票，还是现在就开 map？
   - 推荐：先占位；Part 3 材料到了、如果超过一个 session，再开 map。
8. **效率证据与语气**：只用可核实观察 + 「注意力预算/决策带宽」的委婉组织叙事？
   - 推荐：是；标注「本项目观察，不是基准」，不直接点名裁员。

## 三次提交的取证方式

1. 用 `git worktree add /tmp/harness-talk-<commit> <commit>` 检出三个历史版本。
2. 在对应 worktree 起本地静态服务，用 headless Chrome 截 360×800@2x。
3. 只截与论点有关的屏，不追求完整拼图；每张图注明 commit、时间和「提交时间≠决策时间」。
4. 截图存 `design/harness-era-talk/assets/prototypes/`，页面内可点击放大。

- 不改 app 实现；新 deck 是独立子项目。
- 不把 `.scratch` 当团队文档；团队权威是 GitHub issue。

- 不截 secrets、`.env`、未脱敏日志；对外版删掉内部 issue 编号和具体提交时间。
- 原型是决策工具，不是第二套产品；开发完成后留档封存，不长期维护。
